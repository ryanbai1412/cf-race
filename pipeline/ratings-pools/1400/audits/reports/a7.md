## Method (same for every problem)

1. **Statement and checker.** I read each statement. All six are batch problems with stdin/stdout, a unique answer under token comparison, no interaction, no file I/O and no float tolerance (`floatEps: null`). There is no special checker; `pipeline/checker.py` compares tokens exactly, except that `YES`/`NO` are case-insensitive.
2. **Input validation.** My own strict validators (`v<ID>`) checked every official, open-r1-generated, authored and sample input against the full statement constraints: token counts, ranges, primality for 284A, permutation and string length for 920C, and a digit string with at least one digit >1 for 515C. They normalize CRLF to LF and otherwise reject malformed whitespace. No violations were found. Every coverage claim (boundary, maxSize, adversarial) names a real authored test, and I checked each label against that test's content.
3. **Expected outputs.** My own solvers (`s<ID>`) are written from the statement, not copied from the oracle or generator. They matched every stored output. Brute-force solvers (`b<ID>`) cross-checked small inputs (counts below), and 400 randomized rounds per problem plus all primes below 400 for 284A passed. Number of stored pairs (brute-force checks): 79B 181 (164), 284A 188 (50), 928B 201 (188), 920C 282 (267), 934A 183 (183), 515C 197 (50). There were 0 mismatches after CRLF normalization.
4. **Generator and oracle.** I re-ran each generator twice at seed 42 in the pinned sandbox. Both runs produced byte-identical output, and the SHA256 matches `generation.json` `repeatOutputHashes`. Each package has 150 authored pairs and 150 distinct inputs (mode `extensive`, at least 100). I re-ran each oracle over all tests and samples in the sandbox and got AC. The source hashes of the generator and oracle match `generation.json`, `oracle.json` and `oracles/index.json`. The oracle author (a `devin-oracle-session-*`) differs from the generator and validator author (`devin-1400-worker`), and the oracle source is not a copy of the generator or of any counted submission.
5. **Attribution.** All 10 counted sources per package match the pinned `open-r1/codeforces-submissions@07e7bf31f284b0e90e02dfc7ab675d5821e1c068`: parquet path, size and SHA256, submission ID, problem, language, verdict, testset `TESTS`, and source SHA256. Statement and test rows match `open-r1/codeforces@fbe3f6e903ee854eec2e69e9d96d0306cde59baf`.
6. **Sandbox reruns.** These used `pool_sandbox.run` with `--network=none`, `--read-only`, user 65534, `--cap-drop=ALL`, `no-new-privileges`, `--pids-limit=64`, 1 CPU and 1280m memory, on image `python@sha256:5887f265…105d3`, with `g++ -O2 -std=c++17 -DONLINE_JUDGE` and the package time and memory limits. No downloaded code ran on the host. Each package's 5 accepted submissions passed the whole suite (AC). Each of its 5 incorrect submissions failed on exactly the recorded failedTest with the recorded verdict.
7. **Pitfall (a), CRLF.** I re-ran each incorrect submission on its failedTest with CRLF normalized to LF. The verdict stayed the same for all 30. The canonical Python `input()`-based accepted solutions are AC on the CRLF tests.
8. **Pitfall (b), genuine attempt.** I read every incorrect source. Wherever a source had a debug print, echo or format quirk, I removed only that quirk and re-ran it in the sandbox on LF tests to see whether the recorded failedTest still fails.
9. **Contract.** With `audits/<ID>.json` in place, `pool_contract.verify_evidence` and `publication_gate(require_approval=False)` pass for 928B, 920C and 515C. I wrote no audit file for the rejected problems.

## 79B — REJECTED

All other checks pass: hashes, validation, outputs, determinism (`f3c4fc1a…0fc7` twice), oracle AC, attribution, 5 AC, and 5 incorrect failing as recorded on both CRLF and LF. Two counted incorrect submissions are **not genuine counterexamples on their recorded failedTest**:

- **30810861** (failedTest 0001, WA): the code has a stray `print(s)` that dumps the internal rank dictionary before the answers. With only that line removed, test **0001 is AC**, so its recorded failure is a debug-print artifact. The program fails elsewhere (RE on 0004 because the O(nm) dictionary is too large), but its counted test does not show an algorithmic error.
- **35274405** (failedTest 0001, WA): it prints `waste` instead of `Waste`, and the checker compares that token case-sensitively. After changing only that casing, **0001 is AC**, so the recorded failure is output-format-only. It has a real bug, the inner loop running to k=`a[3]` instead of m, but that bug first shows on 0003, not on the recorded test.

Genuine incorrect submissions: 10600338 (WA 0002, wrong crop-rank formula: prints Kiwis/Carrots for Carrots/Waste), 14550469 (WA 0007, waste cells after the query position are not excluded correctly), 30040253 (TLE 0004, full grid scan per query on a 39898×39898 grid).

Fix: replace 30810861 and 35274405 with incorrect submissions whose recorded failedTest exposes the algorithmic defect.

## 284A — REJECTED

All other checks pass: determinism (`62a7c7fa…a4aa` twice), oracle AC, attribution, 5 AC, and the incorrect submissions fail as recorded on CRLF and LF.

- **3671053** (failedTest 0001, input `3`, WA): it echoes `x=p-1` (`print(x)`) before the answer, printing `2\n1` where `1` is expected. With only the echo removed, **0001 is AC**, so the recorded failure is an echo/debug artifact. Its counting bug (the `j` range stops at `i-2`) only shows on 0002.

Genuine incorrect submissions:
- 3718084 (TLE 0007, p=1583): computes phi(p-1), but `i+=1` is indented inside `if not n%i`, so once i stops dividing n (i=3 for 791) the loop never ends.
- 3718116 (TLE 0007): the same misindented `i+=1` in phi causes the same infinite loop on 1582.
- 4738550 (WA 0009, p=2): the candidate loop starts at 2 and skips x=1, the only primitive root of 2, so it prints 0 instead of 1.
- 13229342 (TLE 0007): checks each candidate with unreduced powers (`x *= num`, never taken mod p), so the bignum arithmetic is roughly O(p²).
