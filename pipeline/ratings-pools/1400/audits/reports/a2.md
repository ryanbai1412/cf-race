## Per problem

### 107A: REJECT
Hashes, statement, constraints, outputs, oracle, generator determinism and coverage all pass. The `algorithmicallyWrong` check fails:
- **9819565** is `print("x")`. There is no algorithm, so no algorithmic defect can be named.
- **37558696** follows each tank to its tap correctly but never prints the count line `t`. On 0001 it prints `1 3 10` where `1\n1 3 10` is expected. This is an output-format omission, not an algorithmic defect.
- **5408132** also omits the count line, which is what makes it fail on 0001. It does have a real defect too: it starts chains at every house with no incoming pipe, including isolated ones, so `1000 0` would print 1000 bogus lines. The failure on its failedTest, though, is the format omission.
- 27308114 is algorithmic. Its union-of-sets approach turns a closed cycle into a reported pair, so 0002 (a 3-cycle) prints `2 …` instead of 0. 30302698 is algorithmic as well: it treats isolated houses as tank/tap pairs, so 0011 (`1000 0`) prints 1000 `i i inf` lines.

Two or three of the five counted incorrect programs are not algorithmically wrong on their failedTest. The pool needs replacement incorrect submissions.

### 175A: REJECT
All other checks pass. **15770608** prints the input string (`print(g)`) before the answer, so on 0001 it outputs `1234\n37` and fails only because of that debug echo. Its 37 is correct. The program does have a latent bug: it rejects a single `"0"` part as having a leading zero. That bug does not cause the failure on its recorded failedTest 0001. The other four are algorithmic:
- 14702816 limits the first part to at most 4 digits and has broken j bounds, so 0004 gives -1 instead of 3000000.
- 14702891 uses `break` on a leading-zero c where it should `continue`, so 0016 gives -1 instead of 947035.
- 42333877 parses s as an int, which loses leading zeros and the digit positions, so 0004 gives 2000001.
- 193699107 has no leading-zero or 1e6 checks and prints twice, so 0003 `0009` gives `-1 0`.

### 261A: REJECT
All other checks pass. **4390055** implements the correct greedy (sort descending, pay for q, skip 2) but prints the debug list `[100, 100, 50, 50]` before the answer, which is the only reason it fails on 0001. **24459839** is a submission for a different problem: it capitalises the first character of the input. It has no algorithm for 261A. The other three are algorithmic:
- 21916773 takes its free items from the cheap end of the list instead of the next most expensive, so 0004 gives 46114 instead of 38578.
- 21918207 calls `sorted()` without assigning the result, so it works on unsorted strings and gets the indexing wrong; 0004 gives 40199.
- 30185746 steps by 2c instead of c+2 and adds n%c of the cheapest items, so 0004 gives 35629.

### 272B: APPROVE
All 11 checks verified. Incorrect submissions:
- 47719996 (WA@0004): it only sums popcount buckets 0..n-1 (`range(n)`), so n=6 with every popcount ≥ 6 gives 0 instead of 2.
- 54885453 (WA@0001): it counts adjacent equal pairs after sorting (k-1) instead of C(k,2), so `1 2 4` gives 2 instead of 3.
- 54885605 (WA@0004): its norm() is not a canonical representative of f (7 and 11 both have f=3 but get different norms), so 0004 gives 0.
- 75475383 (TLE@0012): O(n²) pair loop at n=1e5. It was still running when killed at 6 s in the sandbox (TL is 2 s).
- 129896253 (WA@0004): it uses `answer =` instead of `+=`, and its recursion checks the parity of no//2 (calculate(5)=1 while f(5)=2). 0004 gives 1.

### 289B: APPROVE
All 11 checks verified. Incorrect submissions:
- 3746791 (TLE@0016): it tries every target 0..1e4, which is O(n·m·1e4). On 0016 (53x91) it took 2.7 s CPU in my sandbox against the 2 s TL, and its output was correct. The evidence and CF both record TLE, and the 100x100 tests are worse. The margin on 0016 itself is moderate (about 1.35x the TL).
- 4039763 and 4803409 (WA@0003): they target the mean instead of the median and print 160 instead of 104.
- 18764386 (WA@0003): it targets the element nearest the mean and prints 108.
- 7253300 (WA@0002): it compares a[0][0]%d with the maximum residue rather than checking every residue, so `6 7` with d=7 gives 0 instead of -1.

### 388A: APPROVE
All 11 checks verified. On 0010 (four 1s and six 2s) the answer is 4:
- 5888189 (WA@0010) builds strictly decreasing chains and ignores capacity, giving 6.
- 9089117 (WA@0010) outputs the maximum frequency, giving 6.
- 9126570 (WA@0010) uses strictly increasing first-fit piles, which equals the maximum frequency, giving 6.
- 9245036 (WA@0010) computes max(b[i]-i), which is also the maximum frequency, giving 6.
- 5898411 (WA@0021) tracks capacity only by the newest box, so it over-fills piles and prints 1 instead of 3.

### 41B: APPROVE
All 11 checks verified. Incorrect submissions:
- 5056958 (WA@0020) maximises the per-dollar price difference and ignores how many dollars it can buy, giving 1556 instead of 1682.
- 9382036 (WA@0020) picks the most negative difference with a cheaper-buy tie-break, giving 1172.
- 27681704 (WA@0020) chooses the day with the largest per-unit gain, giving 1172.
- 61597190 (WA@0020) maximises the real ratio a_j/a_i and ignores the integer floor, giving 1172.
- 25366403 (WA@0001) has both loops over range(n-1), so it never uses the last day; `2 4 / 3 7` gives 4 instead of 8.
