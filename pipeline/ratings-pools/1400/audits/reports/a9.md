2. **Statement and checker.** I read each statement. None is interactive, none uses file I/O, there is no float tolerance, `specialJudge` is false, `floatEps` is null, and each has a unique answer under the pool token checker. That checker is `pipeline/checker.py`, which compares tokens and treats YES/NO case-insensitively.
3. **Input constraints.** I wrote my own strict validators (`v<ID>`), without importing the worker recipes or the oracle. ## 762B USB vs. PS/2: APPROVE
- The answer is a greedy: cheapest USB mice to USB-only computers, cheapest PS/2 mice to PS/2-only, then the cheapest leftovers to dual-port computers. Maximise count, then minimise cost (64-bit). The output is unique.
- Coverage, as observed: 0042 a=b=c=0, m=0. 0043 a=b=c=0 (no computers), m=2. 0044 a=b=0, c=2 (only dual-port). 0045 a=b=c=1e5, m=1e5 random. 0046 a=b=c=1e5, m=3e5, all mice 1e9 USB. 0047 a=1, b=1, c=2, where the c computers take one USB and one PS/2 leftover (answer 4 10). 0048 a=b=c=5, m=2.
  - Note: the 0046 label says "overflow sum 1e14" but the actual answer sum is 2·10^14. I read the label as order of magnitude (needs 64-bit, ~1e14 scale), and the rest of the label (m=3e5, all 1e9, USB) is exact. I accepted it on that basis.
- Incorrect submissions (all genuine, same result raw and LF):
  - 26983984 TLE: correct greedy, but uses `del list[0]` in a loop, which is O(m^2). 0034 (m=3e5) takes ≥4 s CPU against a 2 s limit.
  - 34499211: sums `USB[:n2]` instead of `PS2[:n2]`. 0001 prints `3 16`, expected `3 14`.
  - 49169307: interleaved greedy fills dual ports prematurely and prints m-a-b-c. 0002 prints `11 …`, expected `8 2345344274`.
  - 51962277: leftovers are concatenated but not re-sorted. 0004 prints cost 2707359447, expected 1840824320.
  - 51962393: sorts `[price, type]` string pairs lexicographically. 0002 prints 2658907549, expected 2345344274.

## 799B T-shirt buying: REJECT
- Hashes, statement, constraints (my validator: distinct p, colours 1..3), outputs, brute force, oracle, deterministic generation, attribution and the 5 accepted (AC on all tests) all pass.
- **Coverage failure.** Adversarial 0034 is labelled "shirt sold via front then not available via back". Its input is `n=2, p=[1,2], a=[1,2], b=[2,1], buyers 2 1 2`:
  - Buyer 1 (colour 2) buys shirt 1 through its back colour.
  - Buyer 2 (colour 1) finds shirt 1 gone and buys shirt 2 through its back colour.
  - Buyer 3 (colour 2) gets -1 because shirt 2 (front 2) is sold.
  - No shirt is ever sold via its front colour, so the stated case does not occur. The test exercises the mirror case ("sold via back, then unavailable via front"). Under the rule that a coverage label must be literally true of the named test, this fails. The other entries check out: 0030 no match, 0031 back match, 0032 n=m=2e5, 0033 6e4 colour-1 shirts with 3e4 colour-1 then 3e4 colour-2 buyers (3e4 -1s), 0035 n=1, m=4.
- Remediation: relabel 0034, or add a test where a shirt is bought via its front colour and a later buyer of its back colour cannot get it, then re-audit.
- Incorrect submissions: all 5 are genuine attempts at this problem. Each was re-run in the sandbox on its `failedTest`, raw and LF, with the same result both ways.
  - 84848544: never removes sold shirts, so the same cheapest shirt is sold again. 0001 prints `200 400 200 200 200 200`. It is also too slow at max size.
  - 97699746 TLE: for every buyer it rescans and deletes from the full shirt list (O(n·m)), and it also sorts prices as strings. 0006 (n=m=2e5) uses >6 s CPU against a 3 s limit.
  - 105205585: deletes the sold shirt from `f`/`b` with `list.remove(value)`, which removes the first equal colour value rather than index k. That shifts the colour arrays out of alignment with prices. 0003 gives the wrong order `… 687685084 341924810 828969071 857690534 …`.
  - 105213630: once the stock is empty it prints exactly `m-n` -1s rather than one for each remaining buyer. 0004 prints the wrong number of `-1`s.
  - 110268195 TLE: a linear scan with `del` over the sorted list for each buyer (O(n·m)). 0006 uses >6 s CPU against a 3 s limit.
- The rejection rests only on the coverage label.

## 803A Maximal Binary Matrix: APPROVE

- Coverage, as observed: 0169 `1 0`, 0170 `1 2` (-1), 0171 `100 10000` (all ones), 0172 `100 1000000` (-1, k at max), 0173 `100 9999` (only the last diagonal cell is 0), 0174 `100 10001` (-1), 0175 `3 4`. All match.

## 958D1 Hyperspace Jump (easy): REJECT

  - The other four are genuine: 37312018 and 37312384 use O(m²) `list.count` (TLE at m≈5e4). 37314534 truncates with `int(eval())`. 37314659 uses integer division `//` (0003 collapses distinct fractions).
- Remediation: replace 37311965 with a genuine incorrect submission, then re-audit.
